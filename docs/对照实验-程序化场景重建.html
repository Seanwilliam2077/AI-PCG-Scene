把场景嵌在文档里

下面这个框里是归档源码本身，不是录像也不是截图。 点开之后它会在你的浏览器里现场烘 9 张程序化贴图、排一遍总平面、 生成四万多个构件再合并 —— 和第 4 节那八轮迭代跑的是同一份代码。 面板里可以改种子、切三个相机预设、拉视场角与太阳方位、开关 GTAO 与阴影。

首次构建约需数秒到数十秒（取决于机器）。 需要 WebGL2，并且能访问 cdn.jsdelivr.net 取 three.js r0.180.0。

为什么要多出一个 index.cdn.html。 归档的 process/threejs_fob/index.html 的 importmap 指向 ./node_modules/three/…，而仓库没有提交 node_modules， 所以它在静态托管上打不开。index.cdn.html 是同一份文件， 只把 importmap 换成 https://cdn.jsdelivr.net/npm/three@0.180.0/… （版本号取自 package.json 的 "three": "^0.180.0"）， 外加两处纯样式改动：滑杆加 min-width:0（否则 264px 的侧栏会把数值读数挤出边界）， 以及窄视口下把侧栏压窄的一段 media query。场景代码 src/*.js 一行没动。 离线复现仍然用原版： npm i 之后 python process/threejs_fob/serve.py 8177。

过程

八轮迭代

每一轮都跑同样四步：渲一张图 → 和参考图并排看 → 找出最刺眼的那一条偏差 → 改规则 → 再渲。 关键是「最刺眼的那一条」：每轮只解决一个主要矛盾。同时改五处，下一轮就说不清是哪处起了作用。

关于这几张图。第 1–7 轮的原始截图在收尾清理时被删掉了。 iter1_early / iter2_tight / iter3_horizon 是事后把当时的相机与光照参数退回去重新渲染的复现图 —— 这几轮改的确实全是这些参数，所以症状是真实的，但几何与配色是最终版。 第 4、6、7 三轮没有属于自己的画面，播放器里显示的是它们各自「看到问题」时的那一帧， 卡片上会标出来。第 8 轮的 before / after 是真退回那两行错误代码重渲的，差异是实打实的。
这条线最该早点做的事

把「取景」从目视调参变成一次求解

第 3、5、6 三轮都在同一条轴上来回横跳：fov 26°→38°（找回前景周界）→ 补网格排数（填住顶边）→ fov 38°→34°（把纵深收回来）。绕了一圈，落点在 26° 和 38° 之间。 原因很简单：没有一个量在告诉我离目标还有多远。

而这个量并不难写。相机位姿是已知的 —— main.js 的 VIEWS.cam0 给出机位 (2, 100, 272)、目标点 (−8, 5, 88)， 于是俯角 、机高 100 m 都是定的；参考图的两条硬约束也是已知的： 画面底边要压住周界土路（layout.js 的 OUTER_ROAD = 162）， 画面顶边不能越过最远一排院落。把这两条写成不等式，fov 就只剩一个可行区间。

院落排数
垂直视场角 fov 34° 记录里出现过的取值

纵轴是画面顶边射线打到地面的 z 坐标，横轴是 fov。 三条水平线是三种院落排数下最远一排的外沿。曲线在某条水平线之上， 说明顶边仍落在基地里；掉到线下，顶边就越过了基地 —— 也就是「露出地平线」。 点图例开关曲线，点图上任意一点会把上面的滑块跳过去。

解出来是一个区间，不是一个值。 底边要压住周界土路 → fov ≥ （与排数无关）； 顶边不能越过最远一排 → fov ≤ 上限（随排数变）。
院落排数最远一排外沿 zfov 上限可行区间结论

6 排时可行区间是空的 —— 无论 fov 怎么调都同时满足不了两条约束， 必须先把网格铺大。这正是第 5 轮那次「扩排数」的真正理由，而当时是靠肉眼一轮一轮试出来的。 11 排时区间是 ，最终采用的 34° 几乎正好落在区间中点。

这个模型对不对？拿文档里另外三个数字回代验证

模型只有三行：俯角 = atan((机高 − 目标高) / 水平距离)； 边缘射线角 = 俯角 ± fov/2；落点 = 机位 z − (机高 / tan 射线角) × cos(方位偏角)。 下面三行不是拿来拟合模型的，是模型解完之后拿旧记录去核的。

数据结构

总平面：一份数据，两处消费

LOD 只按离相机的排数递减：dist ≥ 4 → 2、dist ≥ 2 → 1、其余 0。 最远七排（LOD 2）里 T 墙退化成一整段盒子，省掉九成构件。

院落用途LOD离相机 场坪围墙世界矩形 x / z

鼠标移到任意一行，左边总平面上对应的院子会高亮。 「随机填充」的 88 个院落每换一次种子就重排一次， 而前三排、周界、道路网格不变 —— 这就是「换 seed 是另一座基地，不是另一堆噪声」的全部含义。

一处需要更正的旧记录。上一版文档写的是「11 列 × 9 排」，且说最远五排为剪影。 按归档 layout.js（COL0 = −5, COL1 = 5, ROW0 = −8, ROW1 = 2） 实际是 11 列 × 11 排 = 121 个院落，LOD 分布 22 / 22 / 77（最远七排剪影）。 121 这个数与旧文档自己给出的「121 院落」、以及本次实测的 __fob.info.cells = 121 都是一致的 —— 错的只是「9 排」这个说法。 第 5 轮那句「z 一直铺到 −398」也对应 row = −8，即 11 排。 第 5 节的排数选择器把 9 排和 11 排都留着了：两种取值下 fov 38° 都超上限、34° 都在区间内， 结论不受影响。

三个观察模式

按顺序叠：沙土底色与大尺度色斑 → 压实道路 → 院内混凝土场坪（含分仓缝与裂缝）→ 停机坪圆圈和 H → 轮胎印 → 油渍与碎屑 → 高频颗粒 → 边缘向远景过渡。为什么不用一堆 plane 拼： 拼贴会有 z-fighting 和接缝，还要额外几十次绘制；烘一张图只要一次。 轮胎印、油渍这种「跨越道路和场坪」的东西，拼贴根本画不了，画布上随手一笔就有。 高频细节交给一张 512² 的沙地法线按 240× 平铺 —— 大结构和小颗粒各管各的。

测法：两张 1200 × 677 的 JPEG 按 Rec.709 转亮度后逐像素相减， 梯度取相邻像素差的绝对值均值。四个区域的坐标是从「差值大于阈值」的连通域里量出来的， 不是手画的。

① 窗套把窗洞盖住了

本意是画一圈窗套，实际写成了一整块比窗洞还大的板，盖在洞口外侧。 远看就是一片浅色方格 —— 参考图里那种密集的黑窗格全没了。改成上下左右四条边框即可。

- b.box('concrete', ww+0.3,  wh+0.3, 0.09, ..)  // 一整块板
+ b.box('concrete', ww+fw*2, fw,     0.1,  ..)  // 上
+ b.box('concrete', ww+fw*2, fw,     0.1,  ..)  // 下
+ b.box('concrete', fw,      wh,     0.1,  ..)  // 左 / 右

② 波纹密到糊成光面

波纹贴图横向有 8 道棱，间距由 tile（多少米一张贴图）决定。 原来给了 0.55，算出来 6.9 cm 一道，远小于一个像素，直接被采样糊成噪点。 改成 2.2 → 27 cm 一道，正好是真实集装箱的尺寸。

- tile: 0.55   // 6.06m / 0.55 * 8 = 88 道 -> 6.9 cm
+ tile: 2.20   // 6.06m / 2.20 * 8 = 22 道 -> 27  cm
这两个 bug 说明一件事：闭环迭代的「比对」环节必须多尺度。 只在主图机位比，远景对了就以为收敛了；真正的模型错误藏在近景里。 探针里那个「远景建筑」区域是同一处窗套改动在 300 m 外的效果： 同一行代码，近景动了 0.18 档，远景只动 0.02 档 —— 主图机位根本报不出这个 bug。 放到 UE5 那条管线上，对应的就是装配完不能只截一张对齐机位图，还得按物件逐个出近景回执。

测法同上：两图缩到同尺寸、各做 σ=1.5 的高斯滤波（滤掉后期那层随机颗粒， 否则 26% 的像素会被颗粒本身的振幅淹没），再逐像素比亮度。滤波后两图相关系数 0.9937， 确认是同机位同一帧。

几何组织

四万个构件，十四个网格

没有用 InstancedMesh。所有物件在同一个矩阵栈里就地生成 —— 墙、楼、卡车、天线一律直接吐世界坐标的几何，按材质丢进桶里，最后每桶 merge 成一个 Mesh。

b.save().at(x, 0, z).ry(ry);
b.box('concrete', w, H, d, 0, H/2, 0, { color: bodyColor, tile: 5.5 });
b.restore();
  • 颜色走顶点色。同一个 concrete 材质能同时当墙、楼、掩体、路缘石， 颜色变化不需要拆材质 —— 这是「十几次绘制」的前提。
  • UV 按世界尺寸重排。boxUV() 把盒子每个面的 UV 按米缩放， 所以 3 m 的墙和 30 m 的楼纹理密度一致，不会一个糊一个碎。
  • 发射几何时顺手烘接地暗部。按世界高度把顶点色压暗一档，物体才「坐」得住 —— 这是在没有实时 GI 的前提下最便宜的接触感。

材质桶：声明 13 个，这一局用上 12 个

材质桶用途粗糙 / 金属源贴图 调用点实测顶点

「调用点」是在 src/*.js（不含 textures.js 的声明处）里 该桶名作为字符串出现的次数；「实测顶点」是种子 20260813 那一局合并后每个 Mesh 的 position.count。concreteDS 的调用点是 0 —— 它被声明为「薄壳双面混凝土」，但天线反射面和旋翼桨叶最后都走了 paintDS， 所以这个桶从来没有被填过，运行时也就不会生成对应的 Mesh。旧文档里的「13 个 draw call」， 准确说法是：声明 13 个材质，实跑产生 12 个构筑物 Mesh，加地面 2 层共 14 个。

诚实

这个循环的短板：它是目视驱动的

回头看，这八轮有一个方法论上的硬伤：判据全在眼睛里。 每轮都是把渲染图和参考图并排看、挑最刺眼的一条改，没有任何可测量的量。 仓库里的线 3 把这个陷阱写得很清楚 —— 「人眼对整体亮度极不敏感、对局部错位又极敏感，凭感觉调会在两三轮后开始互相抵消」。

应验一：三轮在「取景」这一条轴上反复横跳
轮次改的是同一件事结果
3fov 26° → 38°找回了前景周界，但纵深随之超出基地范围
5网格 6 排 → 更多排补地面去填顶边，治的是第 3 轮带出来的症状
6fov 38° → 34°又把纵深收回来 —— 绕了一圈回到 26° 和 38° 之间

第 5 节已经把这条轴解掉了：两条不等式，一个可行区间，一次求解。 需要的判据甚至不必是浮点数 —— 一个布尔量「画面顶边的射线是否仍落在基地范围内」就够。 它本来就是相机反解那个方程的第三个约束，只是当时没写成代码。

应验二：整图指标看不见 GTAO，也看不见远景的窗洞

第 8 节量出来：GTAO 让整图平均亮度只变了 0.021 档，但让 12.9% 的接触区像素暗了 0.13 档。 第 7 节量出来：同一处窗套修复，近景 0.18 档、300 m 外 0.02 档。 如果当时真的挑了一个「整图平均亮度」当判据，这两件事都会被判成「没变化」。 先想清楚指标要判什么，再选指标 —— 线 3 花一整节定目标函数就是在做这件事。

没能补上的：这条线始终没有一个跨轮次可比的分数

诚实地说，本页能补的只是取景这一条轴，因为它的约束是几何的、可以闭式求解。 「明度」「密度」「材质密度」那几轮仍然没有量 —— 第 1–7 轮的原始截图已删， 现在也没法回头补测每轮的指标轨迹。线 3 那张九步指标曲线，本线拿不出对应的东西。 这是记录方式的代价：删掉的中间产物没法事后量化。

可以直接搬走的结论：闭环迭代的价值上限，取决于判据的质量，不取决于循环的次数。 目视驱动能收敛，但会在同一条轴上来回走；一旦某个偏差能被写成一个数（哪怕是很粗的数， 哪怕只是一个布尔量），那条轴上的迭代就退化成一次求解。

三条路线是互补的，不是替代关系。 资产库管线解决「能不能交付」，线 3 解决「像不像这一张图」，本文解决「能不能长出一千张这样的图」。 真正值得移植回主线的不是程序化本身，而是闭环 + 判据这一对： 装配完不是终点，而是下一轮的输入；同时那个「比对」环节必须落成可测量的量。 本文八轮里有五轮的问题（取景、明度、密度、纵深、近景几何）在单向前馈的管线里根本不会被发现 —— 因为没人回头看结果。
复现

怎么跑起来

cd process/threejs_fob && npm i        # 唯一依赖：three.js ^0.180.0
python process/threejs_fob/serve.py 8177
# -> http://127.0.0.1:8177

或者不装依赖，直接开本页第 2 节的内嵌版 index.cdn.html（走 CDN 取 three.js）。

两个环境坑

① Windows 上不要用 python -m http.server：它从注册表读 MIME， .js 会被解析成 text/plain，浏览器直接拒绝加载 ES module —— 配套的 serve.py 把 MIME 表写死了。

② 源码分层：rng.js 可复现随机源 / textures.js 程序化贴图与材质 / builder.js 变换栈与分桶合并 / layout.js 总平面 / ground.js 地面烘焙 / props.js 构件库 / buildings.js 建筑 / vehicles.js 载具 / base.js 摆放 / main.js 渲染与 UI。共 3 163 行。

参考图给的是「长什么样」，代码要回答的是「按什么规则长成这样」—— 把规则写对了，换个种子它还是一座讲得通的基地。
本页所有可交互部件的数据都来自本仓库：图像取自 process/figures/fob/， 几何常量与院落用途取自 process/threejs_fob/src/， 运行时统计取自把该源码跑起来后读回的 renderer.info 与 __fob.info， 像素差值由这几张图现场量出。
